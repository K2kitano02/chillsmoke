## サービス概要

ChillSmoke は、完全禁煙を前提にせず「まずは本数を減らす」ことを支援するアプリです。

喫煙本数を記録すると、設定した基準本数との差から節約額を計算し、欲しいものの購入に使える金額として表示します。
「減らせた本数」を数字だけで終わらせず、金額やウィッシュリストの進捗に変換することで、減煙を続ける理由を作ることを目的にしています。

また、喫煙は日々の習慣と結びつきやすいため、毎回細かい入力を求めるのではなく、`+1` 記録やスケジュール反映など、少ない操作で記録を続けられる導線を重視しています。

## 開発背景

実家を出て生活費を意識するようになり、タバコ代の負担を強く感じたことが開発のきっかけです。

禁煙アプリは「完全にやめる」ことを前提にしたものが多く、少しでも吸ってしまうと失敗したように感じやすいと考えました。
そこで、禁煙できない自分を責めるのではなく「昨日より減らせた」「今月これだけ節約できた」と前向きに振り返れるサービスを目指しました。

## サービスの利用イメージ

1. 初回登録後に、減煙前の基準本数、目標本数、タバコの価格を設定します。
2. 日々の喫煙本数を、ダッシュボードの `+1` や日付指定フォームから記録します。
3. 決まった時間に吸う予定がある場合は、喫煙スケジュールとして登録し、当日ログへまとめて反映します。
4. ダッシュボードやカレンダーで日々の記録を確認し、減煙レポートのグラフで直近30日の喫煙本数・目標・節約額の推移を振り返ります。
5. 節約できた金額を使用可能金額として確認し、ウィッシュリストに登録した欲しいものの購入判断に使います。

## 差別化ポイント

既存の禁煙支援サービスは「吸わないこと」を前提にしたものが多く、失敗した日の心理的な負担が大きくなりやすいと考えました。

ChillSmokeでは、完全禁煙ではなく減煙を前提にすることで、吸ってしまった日も記録を続け、次の日以降の改善につなげられる設計にしています。

| 観点 | ChillSmokeでの対応 |
| --- | --- |
| 継続しやすさ | `+1` 記録、0本記録、スケジュール反映により、日々の入力負担を減らす |
| 振り返りやすさ | カレンダーで達成・未達・未記録を分け、減煙レポートで直近30日の本数・目標・節約額の推移を可視化する |
| モチベーション | 減らせた本数を節約額・使用可能金額・ウィッシュリストに変換する |
| データの正確性 | 未記録と0本を区別し、表示だけでログを作らない |
| 設定変更への耐性 | ログ作成時点の設定を snapshot として保存し、過去の計算が後から変わらないようにする |

## 設計・実装で工夫した点

### 記録を続けやすくする設計

喫煙記録は毎日使う機能のため、ダッシュボードから `+1` で記録できる導線を用意しました。
また、決まった時間に吸うようなルーティン化された喫煙は、喫煙スケジュールとして登録し、ボタンひとつで当日分に反映できるようにしています。

記録し忘れた場合でも後から日付指定で登録・修正できるようにし、継続利用の負担を下げました。

この設計により、毎回フォームを開いて本数を入力する必要を減らしつつ、後から正しい本数に補正できる余地も残しています。

### 未記録と0本を分ける設計

画面表示のために当日のログを自動作成してしまうと、未記録の日が0本扱いになり、実際には記録していないのに達成日として扱われる可能性があります。

そのため、ダッシュボードや日付詳細などの `GET` では喫煙ログを作成せず、保存操作が行われたときだけDBに保存する方針にしています。
これにより、未記録・0本・目標達成・未達を明確に分けられるようにしました。

特に継続日数の計算では、未記録日を達成扱いにも未達扱いにもせず、記録が途切れた日として扱うことで、実際の記録状況に近い表示になるようにしています。

### 設定変更後も過去の記録が壊れない snapshot 設計

喫煙ログ作成時に、その時点の目標本数、基準本数、価格、1箱あたりの本数、鬼モード設定を snapshot として保存しています。

これにより、後から設定を変更しても、過去日の節約額や達成判定が現在の設定で再計算されて変わってしまうことを防いでいます。

例えば、途中で目標本数やタバコの価格を変更しても、変更前に記録した日の計算は当時保存した snapshot を使うため、過去の履歴として一貫性を保てます。

### 減煙の変化を振り返れるレポート設計

直近30日の喫煙本数と日ごとの目標を折れ線グラフ、節約額を棒グラフで表示し、日々の記録だけでは気づきにくい減煙の変化を振り返れるようにしました。
2種類のグラフはタブで切り替えられ、日別カードでは各日の本数・達成状況・節約額も確認できます。

未記録日を0本として線でつなぐと、実際には記録していない日が減煙できたように見えてしまいます。
そのため、未記録日は欠損値としてグラフの線を途切れさせ、目標には記録時点の snapshot を使用しています。
また、今日の節約額は確定額のグラフに含めず「今日の節約見込み」として分け、昨日までの確定実績と混同しないようにしています。

### 重複・同時実行への対策

日次ログは `user_id` と `smoked_on` の組み合わせで一意になるようにし、同じユーザーが同じ日付のログを複数作れない設計にしています。

また、購入処理やスケジュール反映など、同時に実行されると金額や本数がずれる可能性がある処理では、transaction と lock を使って二重購入・二重反映・加算漏れを防ぐようにしました。

スケジュール反映では、`user_schedule_reflections` に `user_schedule_id` と `reflected_on` の組み合わせを保存し、同じスケジュールが同じ日に二重反映されないようにしています。
購入処理では、残高確認から購入履歴作成までを transaction 内で扱い、同時操作による二重購入を防ぐ設計にしています。

### Hotwireによる主要操作の部分更新

毎日使う操作である `+1` 記録、ウィッシュリスト購入、スケジュールの有効/停止切り替え、スケジュール反映は Turbo Stream 化しています。

画面全体を再読み込みせず、今日の本数、節約見込み、使用可能金額、flashなど必要な部分だけを更新することで、操作結果をその場で確認しやすくしました。
一方で、通常のHTMLリクエストでも動く fallback を残し、Turbo前提に寄りすぎない実装にしています。

### 技術選定の理由

**Ruby / Ruby on Rails**

Rails は認証、CRUD、DB設計、バリデーション、ルーティングを一貫して扱いやすく、喫煙記録・設定・購入履歴のようなデータ中心のアプリと相性が良いと考えて選びました。
フロントエンドとバックエンドを分けすぎず、MVCの流れに沿って実装できるため、個人開発でも仕様変更と改善を進めやすい点を重視しています。

当初は、学習情報や周辺Gemの互換性が安定しており、卒業制作として実装と検証を進めやすいRails 7.2系を採用しました。
その後、Rails 7.2系のサポート終了に伴い、既存機能のテストと互換性を確認しながらRails 8.1系へ更新しています。

**Devise**

認証周りは、パスワード管理、ログイン状態、パスワード再設定などを誤って実装するとセキュリティリスクにつながりやすい領域です。
そのため、自作セッションではなく、Railsで利用実績の多いDeviseを採用しました。
ChillSmokeでは、ユーザーごとに喫煙ログ、設定、スケジュール、ウィッシュリストを紐づけるため、認証基盤を早い段階で整える必要がありました。

**PostgreSQL**

本アプリでは、1ユーザー1設定、1日1ログ、1スケジュール1日1反映、1ウィッシュリスト1購入履歴など、DB側でも守りたい一意性があります。
PostgreSQLを使うことで、Railsのバリデーションだけでなく、unique indexや外部キー制約でもデータ整合性を担保できるようにしています。

**Hotwire Turbo / Stimulus**

主要操作はRailsの画面遷移を基本にしつつ、頻繁に使うボタン操作はTurbo Streamで部分更新しています。
ReactなどのSPA構成にせずHotwireを採用したのは、Railsのcontroller、view、partialの構成を活かしながら、必要な箇所だけ操作感を改善できるためです。
Stimulusは、パスワード表示切り替えやモーダルなど、画面上の小さな振る舞いに限定して使っています。

**Tailwind CSS**

Bootstrapのように既定コンポーネントへ寄せるより、減煙支援アプリとして落ち着いた暗めの雰囲気を作りたかったためTailwind CSSを採用しました。
ユーティリティクラスで余白、色、レスポンシブ表示を画面ごとに調整しやすく、スマホ幅の表示崩れ修正にも対応しやすい点を重視しています。

**Minitest / RuboCop / Brakeman / GitHub Actions**

金額計算、snapshot、継続日数、重複防止、購入処理などは、見た目だけでは不具合に気づきにくい部分です。
そのため、Minitestで主要ロジックとcontrollerの挙動を確認し、RuboCopでコードスタイル、Brakemanでセキュリティリスクを確認しています。
GitHub Actionsでもテストと静的解析を実行し、PR単位で品質を確認できるようにしています。

**Render / NeonDB / Resend**

個人開発のMVPでは、インフラ構築に時間をかけすぎず、アプリ改善と動作確認に集中できることを重視しました。
RenderはGitHub連携によるデプロイが扱いやすく、NeonDBはPostgreSQLをマネージドで利用できるため採用しました。
お問い合わせとパスワード再設定メールは、独自ドメインとResendを使って送信できるようにしています。

## ローカル環境構築

Docker を使用して起動します。

```bash
docker compose up
```

DB作成・マイグレーションを行います。

```bash
docker compose run --rm web bin/rails db:create db:migrate
```

テストを実行します。

```bash
docker compose run --rm web bin/rails test
```

RuboCop と Brakeman を実行します。

```bash
docker compose run --rm web bundle exec rubocop
docker compose run --rm web bin/brakeman --no-pager
```

### 本番環境で必要な環境変数

Render では、問い合わせメールとパスワード再設定メールを Resend 経由で送信するため、以下の環境変数を設定します。

```text
RESEND_API_KEY=Resendで発行したAPIキー
CONTACT_MAIL_TO=問い合わせを受け取るメールアドレス
CONTACT_MAIL_FROM=Resendで認証済みドメインの送信元メールアドレス
DEVISE_MAILER_FROM=Resendで認証済みドメインのパスワード再設定メール送信元
APP_HOST=chillsmoke.net
```
